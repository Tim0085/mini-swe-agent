## P1：优先处理

### R01 评测摘要丢失基础设施及不明确失败分类

- 类型：结果正确性／错误解释。**已用离线报告样例复现**。
- 位置：`local_setup/webui/bench.py:146` 的 `summarize_report`；`worker.py` 的 `evaluate`；`static/workbench.js` 的 `renderMeta`。
- 触发：报告为 completed=1、resolved=0、errors=0，且 `infra_failure_instances=1` 或 `ambiguous_failure_instances=1`。
- 实际：两者都变成“未通过（请查看详细报告）”，摘要舍弃分类字段及 `failure_reasons`。本机 harness 的 `reporting.py` 明确生成这些字段。
- 影响：用户容易直接归因于模型补丁，并重复求解；历史上本题确实出现过环境／换行问题，因此不能仅凭 unresolved 推断补丁有错。
- 建议：保留原 resolved 统计，同时单独显示“疑似环境失败”“失败原因不明确”及原始依据；不要把这两类自动改成通过。
- 验收：正常通过、测试未通过、基础设施问题、原因不明确、未完成五类均有独立说明；原报告计数原样保留。建议 `/harden`，文案配合 `/clarify`。

### R02 新建文件的内容无法从差异产物检查

- 类型：结果可检查性。**已在独立 Git 仓库复现**。
- 位置：`local_setup/webui/changes.py:49-66`，`server.py` 的 `artifact_list`。
- 触发：任务创建尚未被 Git 跟踪的文件。
- 实际：变化清单正确显示“新增 new_output.py”，但 `git diff -- <path>` 不包含未跟踪文件，生成的 `changes.diff` 是 **0 字节**；网页也没有这些新文件的内容预览。
- 影响：用户能看到“新增了什么名字”，却难以直接检查主要交付内容；普通新项目尤其常见。
- 建议：为新增文本文件生成明确的新增内容预览或补丁，不改用户 Git 索引、不自动暂存。无可导出差异时解释原因，不给空产物造成误解。二进制、大文件及疑似凭据继续明确限制。
- 验收：新增、修改、删除、非 Git 项目分别有准确的结果入口；不因生成预览改变真实项目。建议 `/harden`。

## P2：流程及边界

### R03 已加载题目在刷新后失去准备状态

- 类型：任务流程。**浏览器复现**。
- 位置：`static/workbench.js` 的 `restoreDraft`、`usePrepared`、`updateControls`、`startRun`。
- 触发：加载题目完成 → 选择评测 → 刷新页面 → 点击“开始评测”。
- 实际：补丁选择恢复且按钮可点击，但 `loadedProblem` 为空，点击后才要求重新加载题目。没有创建重复任务或发起模型调用。
- 建议：刷新后按数据集和题号重新检查已有缓存，或在未就绪前禁用开始并在旁边说明下一步。避免把“加载题目”反复变成新的历史任务。
- 验收：刷新后一步即可继续，缓存变化时有明确检查结果；不能凭浏览器旧草稿绕过服务器校验。建议 `/onboard` 或 `/harden`。

### R04 设置冲突提示要求重新加载，但重新进入设置仍继续冲突

- 类型：配置恢复。**双窗口浏览器复现**。
- 位置：`static/workbench.js` 的 `saveSettingsDraft`、`fillSettings`、`loadSettings`、`persistSettings`。
- 触发：窗口 A 把步数改为 55 但未保存；窗口 B 保存 60；A 保存失败，再离开并重新进入设置后保存。
- 实际：A 仍保留旧草稿版本号，再次得到“配置已被其他窗口修改，请重新加载后保存”。可通过放弃草稿解决，但会丢失当前编辑。
- 建议：显示服务器当前值与本地未保存值，提供“载入最新版本并保留编辑待确认”或明确逐项合并；不能静默覆盖另一窗口的修改。
- 验收：冲突后有能真正走通的恢复操作，不需要盲目反复刷新或丢掉全部编辑。建议 `/harden`。

### R05 相同补丁跨模型合并后，对话可用提示可能不准确

- 类型：补丁来源。**数据样例复现**。
- 位置：`local_setup/webui/patches.py` 的 `catalog` 与 `conversation_for`。
- 触发：模型 A 的轨迹与模型 B 的预测文件包含相同补丁。
- 实际：按补丁 hash 合成一项并优先选择 B 的预测；`has_conversation=true` 来自 A 的轨迹，但实际对话匹配要求模型也一致，所以返回 0 条。
- 建议：保留各来源模型与对应轨迹的关系；推荐项的“可查看对话”必须与实际选中来源一致。允许分组展示同内容的不同来源，不混淆生成者。
- 验收：相同内容／不同模型、相同模型／不同内容都保持准确关联。建议 `/harden`。

### R06 首条消息过长会被误报为找不到轨迹

- 类型：长记录。**数据样例复现**。
- 位置：`local_setup/webui/patches.py` 的 `conversation_for`。
- 触发：匹配轨迹的首条非系统消息超过约 200000 字符。
- 实际：读取循环在加入第一条前退出，随后把空消息列表当作无匹配，返回“未找到……历史轨迹”，没有截断提示。
- 建议：区分“找到了但超限”和“未找到”；分段或逐条加载，至少保留来源与截断提示。
- 验收：首条超限、后续超限、空轨迹、损坏轨迹四种情况说明准确，原文不改写。建议 `/harden`。

### R07 长对话缺少“最新消息”定位和按需加载

- 类型：长会话操作／扩展性能。**合成事件经真实 SSE 渲染复现**。
- 位置：`static/workbench.js` 的 `appendMessage`、`openRun`；`server.py` 的 `events`。
- 实际：1600 条样例一次生成 1600 个消息节点，整个页面约 5077 个 DOM 节点、对话约 162 万字符、页面高度约 384447px；位置仍在顶部，最新消息约在 384101px 处。
- 本机加载约 195ms，**本次没有证据证明当前就卡顿**。已确认的问题是定位最新内容不方便，且数据量无分页边界。
- 建议：增加“回到最新”和新消息计数；用户正在回看时不要强制滚动。历史采用逐段加载或虚拟列表，保持请求去重和切换隔离。
- 验收：长会话一键定位最新，回看时视图稳定，页面刷新不会重复消息。建议 `/optimize`。

### R08 评测仍可能长时间只有一行输出

- 类型：进度可理解性。**代码路径确认，未重跑正式评测**。
- 位置：`worker.py` 的 `evaluate`；本机 harness `run_evaluation.py:284-374`。
- 原因：工作台主要转发 harness 的标准输出；创建容器、应用补丁等阶段主要写 `run_instance.log`，测试内容则在执行结束后才写 `test_output.txt`。
- 影响：即使切到“评测进度”，用户仍可能只看到 Running 1 instances 和不断增长的时间，难以区分环境准备、补丁应用或测试执行。
- 建议：读取所属任务的阶段日志，显示最后更新时间和当前阶段；测试没有逐行输出时如实说明，不伪造百分比。评测超时单独标明，避免把页面模型／命令 timeout 当作评测总超时。
- 验收：正式评测时可辨认各阶段；没有输出也能知道后台状态与停止入口。必须在允许执行正式评测后补验收。建议 `/clarify`、`/harden`。

### R09 状态文档和操作说明已有漂移

- 类型：交接可靠性。**只读现场核对**。
- 位置：`collaboration/docs/current-state.md:52`、`runbook.md:41-45`、旧验收摘要。
- 实际：当前 Docker 只读检查可返回 linux，旧文档仍写启动失败；runbook 尚未说明 1.1.1 的补丁合并和历史对话入口。不同段落的 16／21 测试与 6 条历史记录需要区分各自日期和范围。
- 建议：当前事实只保留一份入口；旧报告标明历史快照，不删除旧失败证据。补齐 runbook 的新流程，阻塞项记录“最后核实时间”。
- 验收：后来接手者不会按旧 Docker 结论重复修复环境，也不会把引擎响应当成评测通过。建议 `/clarify`。

### R11 少数折叠入口点击区偏小

- 类型：可访问性／响应式。**390px 浏览器测量**。

- 实际：“浏览文件夹”折叠入口约 20px 高；主导航和主要按钮已至少 44px。复选框本体 18px，但有可点击关联标签，不能只测控件本体就认定违规。
- 建议：把折叠入口实际点击区扩展到约 44px，保留当前层级和键盘行为；本轮未据此作正式 WCAG 不合规结论。
- 验收：触控及键盘都易操作，不挤压窄窗口主要内容。建议 `/adapt`，最后 `/polish`。

# Mini 工作台使用完整性审计

日期：2026-09-15。性质：审查和整理，不实施功能修复。

这是修复前的历史审计，不代表当前代码状态。后续全量修复与证据见 [1.1 修复清单](workbench-fixes-2026-09-15.md)。旧代码位置保留用于解释当时的问题。

## 结论

发现 16 组问题：8 组 P1（优先修复）、8 组 P2（随后完善），未发现需要将整个应用判为 P0 的证据。P2 中的历史接续属于体验缺口，不代表已承诺支持恢复代理会话。

退出按钮缺失是更普遍问题的一个表现：当前实现主要验证了“从开始到提交”的顺利流程，对退出、故障恢复、任务之间状态隔离及长期使用仍不完整。此前 8 项测试通过只证明那些具体路径，不能代表这些边界也已验证。

## 检查边界与证据

- 阅读启动器、服务、任务进程、设置、Docker／评测适配、页面脚本及现有测试。
- 使用独立无头 Edge，不接管用户现有浏览器。只调用会话建立和只读 API，没有启动／停止任务、保存配置或修改密钥。
- 浏览器断网仅作用于新建的测试上下文，不修改系统网络或用户浏览器。
- 本次没有调用模型、下载数据／镜像、安装依赖、启动／重启／结束工作台或 Docker。
- 内存中使用虚构样例核验配置转义及脱敏行为，不写入真实配置或预测文件。
- 程序源文件保持不变，仅新增审计资料和文档导航。
- 复现摘要见 [审计证据](../artifacts/2026-09-15/workbench-audit/findings.json)。代码位置以本次源码为准，后续改动后需重核。

## P1：优先修复

### A01 — 退出流程缺失

- **位置：** `launch.py:29-38,41-85`；`index.html:9-21`；服务没有退出 API。
- **影响：** 关闭浏览器只关闭页面；空闲 Python 服务仍存活，运行中的任务继续。用户无法从界面区分“停止任务”和“退出整个工具”。
- **修复：** 提供“退出工作台”，说明活动任务处理方式；停止本工具所属任务、等待清理完成后关闭服务。保留“仅关闭页面，继续后台任务”的明确选择。不结束其他 Python、Docker Desktop 或用户软件。
- **验收：** 空闲退出、待确认退出、执行中退出、评测中退出均有准确提示；退出后本服务端口关闭、所属进程停止，再次双击能正常启动。

### A02 — 单次授权跨任务延续

- **位置：** `app.js:17,27-33`。开始和返回新建任务均不重置 `auto`／`downloads`。
- **复现：** 勾选自动执行／允许下载，切换任务类型与导航后返回，两个开关仍为 true。没有实际启动任务。
- **影响：** 界面写“本次”，但下一任务可能继续自动执行或下载大镜像，超出用户对单次授权的理解。
- **修复／验收：** 每项新任务独立授权，默认复位；若另设长期偏好必须明确标识。切换题目、复用历史、重试和多标签页都不能悄悄继承一次性授权。

### A03 — 任务切换异步结果相互覆盖

- **位置：** `app.js:21,25-26`，全局 `currentRun`、`source`、`runSequence` 未做请求归属检查。
- **复现：** 对两个已结束任务快速调用现有打开逻辑；8 次中有 4 次最终 `currentRun.id` 不是最后选择的任务。只读取历史，无新任务和批准请求。
- **影响：** 标题、输出和任务状态可能来自不同选择；存在用户判断、停止或确认错误任务的风险。本次没有验证或实施错误命令执行。
- **修复／验收：** 每次打开使用独立代次标识，过期响应直接丢弃；关闭捕获的 SSE 实例而非任意全局实例。快速 A→B→A、慢响应、断线恢复后标题／记录／票据始终同属当前选中任务。

### A04 — 结束状态与清理状态不同步

- **位置：** `server.py:190-209,222-230,91-99`；`worker.py:157-161`。
- **影响：** 停止先写 cancelled，再终止 Job；完成先发 completed，再清容器。页面立即隐藏停止按钮，但服务仍占用活动任务位置，可能出现“已完成却不能开始新任务”。清理失败只留下提示，没有重试；重启恢复跳过 terminal 任务，因此已停止但未清理的容器不会被该恢复分支重试。
- **修复／验收：** 增加“停止中／清理中”，清理完成再结束；清理失败显示所属资源及重试入口，重启检查待清理清单。仅清理自身资源，不强制关闭 Docker Desktop。

### A05 — 草稿与未保存修改丢失

- **位置：** `app.js:18,28,37,41`；`index.html` 没有未保存状态保护。
- **复现：** 未提交任务刷新后描述为空，项目目录恢复安装目录；修改模型名，离开设置再回来，内容恢复旧值且没有提醒。
- **影响：** 任务描述丢失；没有注意到路径复位时，后续可能在错误目录执行。另有保存密钥成功后 `showSettings()` 覆盖同页尚未保存连接设置的代码路径。
- **修复／验收：** 保存非敏感草稿和目录，编辑设置有 dirty 状态，离开时可保留／丢弃；密钥不缓存到浏览器。密钥表单成功不覆盖其他表单草稿。

### A06 — 故障恢复缺少降级页面

- **位置：** `launch.py:54`；`server.py:91-108,325-329`；`settings.py:49-60`；`app.js:41-42`。
- **条件：** service.json、任一任务 meta.json 损坏，配置不满足验证，或 Git Bash 路径失效。
- **影响：** 对文件直接解析、初始化使用全成全败的 Promise.all；一个组件失败可能导致启动／历史／整个初始页面不可用。恰恰在需要修配置时，设置界面也无法正常加载，又退回手工修文件。
- **修复／验收：** 状态文件和单条历史隔离处理；提供可恢复的诊断页与配置备份恢复入口；Git Bash 不可用仅禁用相关任务。用独立测试目录注入损坏文件验证，不破坏真实记录。

### A07 — 新代码与旧服务可能混用

- **位置：** `launch.py:54-55,74-84`；`server.py:285-287`。
- **影响：** 健康检查仅判断实例身份，没有版本或代码变更信息。修改 Python 后再次双击仍复用旧进程，而浏览器会读取新的静态文件，可能出现新按钮对应旧 API 的错误。
- **修复／验收：** 显示服务版本和重启需要；有任务时不静默重启，任务结束后提供受控重启。重启过程不留下双实例，更新后的前后端版本一致。

### A08 — 脱敏静默改变业务输入和补丁

- **位置：** `common.py:28-50`；`server.py:158-164`；`bench.py:43`；`worker.py:155,171`。
- **复现：** 虚构补丁中包含形似密钥的示例字符串，调用实际 `redact()` 后文本不同。保存请求、题目数据和预测时都使用这一脱敏路径。
- **影响：** 用户的合法示例代码、题目测试脚本或补丁可能被替换为 `[REDACTED]`，改变求解／评测内容，却没有提醒。此处并非允许把真实密钥输出或提交。
- **修复／验收：** 展示用脱敏与执行输入严格分离；若产物疑似包含真实秘密，应阻止导出并明确提示处理，不能静默改写后继续评测。对虚构密钥示例做内容一致性测试，实际秘密保持不可泄漏。

## P2：随后完善

### A09 — 断线状态与重试不完整

- **位置：** `app.js:14,26-27,41-42`。
- **复现：** 测试浏览器断网后，甚至设置读取已报 `Failed to fetch`，顶部仍显示“已连接 · 本机”。
- **其他边界：** 首次初始化失败会永久禁用开始按钮，缺少页内重新初始化；创建请求每次生成新 request_id，丢响应后的用户重试不能利用原去重 ID；只有 SSE 路径有部分重连状态。
- **修复／验收：** 统一连接状态与中文错误提示，提供重新连接；保留创建请求 ID，丢响应后先查询已有任务再决定重试。用断网／恢复验证，不制造重复付费任务。

### A10 — 长操作进度与取消不完整

- **位置：** `windows_env.py:29-50`；`bench.py:26-43,74-84`；`server.py:344-347`。
- **影响：** 本地命令输出等 communicate 完成后才显示，下载镜像等 subprocess.run 结束才返回。题目下载在预览请求里，可连续多次等待 60 秒，不属于可停止任务。用户容易把等待误认为卡死；关闭页面也不等于中止服务端下载。
- **修复／验收：** 逐步输出、显示当前阶段与耗时；把长下载纳入可取消作业。取消请求可追踪，断线不重复下载；大输出有截断说明和完整日志入口。

### A11 — 结果入口和文件存在性不一致

- **位置：** `app.js:21,24`；`server.py:404-411`；`worker.py:185-192`。
- **复现：** 读取实际已失败的评测任务，界面“下载预测文件”可见，但请求返回 404。代码按任务类型而非文件是否生成显示按钮；轨迹入口也有类似边界。
- **影响：** 出错时用户无法判断哪些东西已保存。正式报告只显示部分 JSON／路径，没有完整汇总报告、test_output 或 run_instance.log 的下载／定位入口；屏幕日志截取最后 200000 字符也没提示。
- **修复／验收：** 后端返回产物清单和可用状态，仅提供有效入口；错误详情能到达完整日志，早期失败／中断／正常提交分别验证。

### A12 — 配置保存边界与密钥生效保障不足

- **位置：** `settings.py:33-42,49-60,90-116,119-127`；`run.py:25`；`app.js:37`。
- **内存复现：** 带单引号路径的 URL 通过 Settings 验证，但拼入 .env 后无法正确解析；保存只断言模型名，未核对 API Base。正则修改已有 .env 行会把该行 CRLF 变为 LF，原测试只检查了保留行，没有覆盖这一点。
- **条件性问题：** 密钥“已配置”仅检查文件存在，没有验证可解密；旧 .env 如含 OPENAI_API_KEY 会优先于新 DPAPI 密钥。本机当前未发现此明文项，不是当前已发生的密钥错误。密钥输入在请求成功前清空，保存失败需重填。
- **修复／验收：** 安全转义并完整读回新配置；保留编码／换行；明确唯一凭据来源及可用状态；失败不误报成功。用独立文件覆盖这些情况，不调用付费模型。

### A13 — 长期存储及历史规模缺少管理

- **位置：** `server.py:107-108,131-136,414-426`；`settings.py:104-107`；`launch.py:69`。
- **影响：** 日志、任务和每次保存的备份持续累积，没有容量视图、筛选／分页、归档或保留策略。每次列表和创建任务都遍历全部历史；旧记录直接整份 JSON 渲染。尚未进行大量记录压测，不能声称当前已经明显卡顿。
- **修复／验收：** 显示各类空间和任务列表筛选；清理先列精确范围与可保留证据，再由用户确认，默认不删除。任务历史分页，大文件按需读取；不把测试记录与用户正式结果混为一谈。

### A14 — 任务接续和结果复用入口不足

- **位置：** `app.js:19-21,27,40`；`index.html:69-75`。
- **影响：** 结束／失败任务只能回看，没有“复制参数重试”，也没有提交后追问入口；中断恢复只做状态标记，没有上下文接续。普通编程结果仅展示代理提交文本，缺少独立的改动文件清单。非 Django 的旧轨迹还被下拉框的硬编码过滤条件遗漏。
- **定位：** 同上下文续跑是待决策的功能补齐，不是声称已实现的能力。
- **修复／验收：** 先增加复制参数为新任务，并明确会重新调用模型、重置单次授权；呈现实际改动摘要。历史选择按文件类型／实例元数据处理，不按 Django 名称特判。真正续跑另定上下文与费用规则。

### A15 — 任务类型不同，元数据仍沿用隐藏字段

- **位置：** `app.js:21,27`；`server.py:165-168`；`worker.py:169-170`。
- **影响：** 评测任务可能继承先前编程表单里的任务描述和 Windows 目录；Docker 任务详情优先显示隐藏 cwd 而非实际 /testbed。评测历史记录使用当前设置模型，实际补丁却可能来自另一个模型，影响结果归属判断。
- **修复／验收：** 各类型独立构建请求和元数据；评测记录区分补丁来源模型与执行器，Docker 目录显示真实环境。切换类型及修改默认模型后评测旧补丁，标题、目录、模型均保持准确。

### A16 — 可读性与键盘／辅助技术细节不足

- **位置：** `index.html:25-29,70-75`；`app.js:30-31`；`style.css:2-3`。
- **实测：** 占位文字对比度约 3.47:1；390px 下导航 10px 字号、33px 高；6 个 role=tab 均无 aria-controls，右方向键未切换选中标签；任务状态无 aria-live。
- **影响：** 小字和弱对比增加阅读负担；键盘及读屏用户难以了解标签和任务状态变化。33px 高未达到建议的 44px 触控目标，但本报告不将其单独认定为 WCAG 2.2 AA 24px 条款失败。
- **修复／验收：** 正文／占位文字对比与字号足够，键盘标签页行为和关联补全，关键状态可播报，错误定位到字段。保持现有浅色方向，固定浅色和使用本机字体是已确认要求，不算缺陷。

## 应保留的已有能力

- 复用现有环境，前端没有另起大型依赖栈。
- API 会话、来源检查、配置指纹、默认命令确认及输出按文本显示已有基础。
- Job Object 和所属容器命名提供了限定清理范围的机制，修复应补齐生命周期，不改成全局杀进程／清理 Docker。
- 原配置、密钥及历史结果保持原位置；文档和私有运行数据已分层。

## 修复顺序与回归要求

1. **/harden**：先处理 A01–A07，建立退出、清理、任务归属、授权和草稿保护；不改模型推理逻辑。
2. **/harden**：处理 A08、A12、A15，确保输入／补丁、配置、模型归属不被静默改变。
3. **/clarify**：处理 A09–A11、A14 的反馈、诊断、产物可用性与接续提示。
